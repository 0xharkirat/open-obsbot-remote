> into v1.2. See `CHANGELOG.md` for what actually shipped. This doc is
> preserved as a design log so future work can borrow its sequencing
> and verification approach.

## P0 — must fix before v1.1 ships

These break the live-event use case. Ship blockers.

### P0-1 — PTZ sign convention (yaw + pitch inverted)

**Symptom:** "Down button moves camera up. Up button moves camera down."
Almost certainly yaw is inverted too — verified by smoke harness in last
session (`yaw_speed:+60` moved snap_.ptz.yaw from +0.6 to -124).

**Fix path:**
1. Verify physical direction with all 4 axes by smoke harness.
   - Send `pitch_speed:+30, yaw=0` for 1s. Read `lastState.ptz.pitch`.
   - Repeat for `-30`. Repeat for yaw.
   - Build a 2×2 truth table (`speed sign → position direction`).
2. Decide invert layer.
   - **Bridge-side flip** (preferred). Negate `yaw_speed` and/or
     `pitch_speed` once in `cmd_ptz_velocity` so all clients (web,
     iOS, Android, future native) get consistent semantics.
   - Document the convention in `docs/PROTOCOL.md`: positive yaw_speed
     pans right (camera viewer perspective); positive pitch_speed tilts up.
3. Update smoke battery to assert direction explicitly, not |delta|>5.

**Files:** `apps/bridge_cpp/src/device_session.cpp`, `tests/bridge_smoke.mjs`,
`docs/PROTOCOL.md`.

### P0-2 — Joystick swallowed by page scroll

**Symptom:** "If I try to use the joystick it starts scrolling and the
joystick doesn't get the input."

**Cause:** `_buildPortrait` wraps the entire page in `SingleChildScrollView`
(I added that for mobile responsive). Pan gestures inside `PtzPad` race
with the scroll view; on mobile the OS hands them to the scrollable
ancestor first → scroll wins.

**Fix path:**
1. Wrap `PtzPad` widget in `GestureDetector(onPanDown: (_) {})` to claim
   pan, OR use `Listener(behavior: HitTestBehavior.opaque)` to short-
   circuit scroll. OR simpler — use `NeverScrollableScrollPhysics()`
   on the inner area where joystick sits.
2. Better — replace `SingleChildScrollView` with a layout that pins the
   preview + joystick + zoom slider above the fold, scrolls only the
   bottom action rows. Hero controls always reachable without scroll.
3. Same fix needed for `ZoomSlider` (vertical drag could scroll page).

**Files:** `apps/rc/lib/control_screen.dart`.

### P0-3 — Directional buttons flaky

**Symptom:** "Sometimes work, sometimes don't."

**Likely cause(s):**
- `_HoldDirBtn` uses `Listener.onPointerDown/Up`. If a touch starts as
  scroll-pan elsewhere it bubbles to the listener inconsistently. Same
  scroll-conflict as P0-2.
- Bridge velocity coalesce drops `<30ms` repeats. If two presses fire
  near-back-to-back the second is ignored.
- Camera firmware AI-tracker race — if AI mode is mid-transition when
  a velocity tick lands, camera ignores. Already mitigated by
  `ai_disabled_for_manual_` flag + 50ms settle but only on first cmd.

**Fix path:**
1. Eliminate scroll conflict (P0-2). That alone may fix this.
2. Add bridge log per `cmd_ptz_velocity` invocation (rate-limited info
   line) so we can correlate "pressed but no move" against actual SDK
   call counts.
3. Add a smoke test that hammers Left + Right alternately at 250ms
   intervals × 20 cycles, asserting yaw oscillates.
4. Visual feedback: flash the held button red briefly on each tick so
   the user can see whether their press registered.

**Files:** `apps/rc/lib/control_screen.dart`,
`apps/bridge_cpp/src/device_session.cpp`, `tests/bridge_smoke.mjs`.

### P0-4 — Zoom intermittently fails (real-world)

**Symptom:** "Zoom is still not always correctly working."

Different from the smoke-test scenarios — likely timing-dependent under
real touch input. Possible causes:
- Mid-drag throttle (tiny step + <80ms) drops the user's terminal value
  if the drag-end pos differs by <0.1× from previous tick.
- `pending_zoom_` not cleared if camera never reaches target (e.g.
  command failed silently).
- Multiple clients (phone + bridge UI both read state) racing.

**Fix path:**
1. On `onChangeEnd` in `ZoomSlider`, send a final `zoom.set` with the
   exact slider value AND tag it as terminal (new field `final: true`)
   so the bridge bypasses coalesce. Already accept zmin/zmax but not
   intermediate finals.
2. Telemetry: bridge logs every `zoom.set` action with input value,
   coalesce decision, SDK return code.
3. Stress test: drag-end at 50 random values 0.1× apart, assert each
   reaches snap_.zoom.

**Files:** `apps/rc/lib/control_screen.dart`,
`apps/bridge_cpp/src/protocol.cpp`,
`apps/bridge_cpp/src/device_session.cpp`,
`tests/bridge_smoke.mjs`.

### P0-5 — Sequencer zoom snap-mismatch

**Symptom:** "Sequencer with presets with zoom in and out are very fast
even though gimbal movement is slow but zoom is super quick. Looking at
it is very bad."

**Cause:** `cmd_preset_recall` picks a fixed `zspeed` per `MoveSpeed`:
slow=3, medium=6, fast=9, instant=10. Gimbal duration depends on
distance + the same speed enum but mapped to `gimbalSetSpeedPositionR`
parameters (which produce ~5×–20× different durations). Zoom motor and
gimbal motor reach their target on different timelines. Visually jarring.

**Fix path:**
1. Compute *expected gimbal duration* from `(yaw_delta, pitch_delta,
   roll_delta, speed)` using the camera's known motor rates. Bridge
   already stores `speed_to_rates(...)` — extend to return ms.
2. Compute zoom delta seconds independently (`abs(zoom_target - zoom_now)
   / zoom_motor_rate`), pick a zoom_speed that lands the zoom move at
   the same time as gimbal arrival.
3. If exact match isn't possible, bias slower (zoom finishes after
   gimbal) — feels much better than zoom finishing first.
4. New protocol field for sequence step: `zoom_match_gimbal: true`
   (default true). Phone UI hides the field; advanced users can override.

**Files:** `apps/bridge_cpp/src/device_session.cpp` (cmd_preset_recall +
sequencer trigger),
`apps/rc/lib/sequencer_screen.dart`,
`tests/bridge_smoke.mjs`.

## P1 — features for v1.1

### P1-1 — Cinema-slow speed tier

**Goal:** "Wedding-movie slow." Camera motor floor.

**SDK:** `gimbalSetSpeedPositionR(roll, pitch, yaw, sr, sp, sy)` accepts
speed values where lower = slower. Current `slow` maps to `sr=10, sp=15,
sy=20`. Camera firmware accepts down to `sr=1, sp=1, sy=1` — needs
testing for actual motor minimum.

**Fix path:**
1. Add `MoveSpeed.cinema` (slowest) below `slow`. Map to
   `sr=2, sp=3, sy=4` initially; tune empirically with smoke timing.
2. Plumb to protocol: `speed: "cinema"` on `preset.recall` and sequence
   step, AND on app-wide move-speed selector in control screen.
3. Smoke test: recall preset twice, once at `slow` and once at
   `cinema`, time both. Assert cinema > 3× slow duration.
4. Bridge log so user can verify motor actually accepted the slow value.

**Files:** `apps/bridge_cpp/src/device_session.h`,
`apps/bridge_cpp/src/device_session.cpp`,
`apps/bridge_cpp/src/protocol.cpp`,
`apps/rc/lib/ws_client.dart`,
`apps/rc/lib/control_screen.dart`,
`apps/rc/lib/sequencer_screen.dart`.

### P1-2 — Exposure / EV bias controls

**Why:** User saw "very dim" output today caused by manual auto-exposure
toggle in OBSBOT Center. Bridge should expose this so users can fix it
inside our app, not need OBSBOT Center.

**SDK:** `cameraSetExposureModeR(mode)` (0=unknown, 1=manual, 2=allauto,
3=aperture, 4=shutter); `cameraSetAAEEvBiasR(bias)` enum -3.0 to +3.0
in 1/3 stops. Both tagged "tail air" but worth probing on Tiny 2 Lite.

**Fix path:**
1. Bridge: probe both APIs at startup; log whether they return 0.
2. New actions:
   - `image.set_exposure_mode mode: "auto" | "manual"`
   - `image.set_ev_bias bias: -2.0 .. +2.0`
3. Phone UI: Advanced screen → new "Exposure" section with mode toggle
   and EV slider. Hide if SDK reports unsupported.
4. Persist to `image.json` so reset doesn't lose the value (also covers
   yesterday's HDR-on-restart issue).

**Files:** all bridge_cpp + rc/lib/control_screen.dart.

### P1-4 — forui migration

**Why:** Material widgets are functional but generic. forui has
better-looking buttons / sliders / tabs / dialogs that work well on
small screens and look like a deliberate design system.

**Strategy:**
1. Add `forui` to `apps/rc/pubspec.yaml`.
2. Convert *one* simple component first as proof — e.g. the "Pair"
   screen's PIN textbox + submit button.
3. If happy, migrate per-screen: pair → simple → control → sequencer.
4. Keep Material as fallback for widgets forui doesn't have (e.g. some
   sliders).
5. Ship behind a settings toggle for one release before making default.

**Files:** every screen in `apps/rc/lib/`.

### P1-5 — Production UI redesign

**Goal:** consistent, mobile-first, accessibility-AA.

**Design doc** — `docs/UI_SPEC_V1.1.md`:
- Breakpoints: phone-portrait (<480), phone-landscape (480–800), tablet
  (800–1200), desktop (>1200).
- Each breakpoint: explicit wireframe for control screen + simple +
  sequencer + pair.
- Touch-target floor: 44×44 (iOS HIG).
- Color tokens, type ramp, spacing scale (extend material 3 base).
- Copy review (button labels, error messages, empty states).
- Skill `design:ux-copy` and `design:design-system` apply.
